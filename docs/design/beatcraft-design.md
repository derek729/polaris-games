## 1. 목표 (재미 문제)

BeatCraft는 "클리어" 이후의 목표가 수평이다. 판정 윈도우가 지나치게 관대해(PERFECT ±55ms, BAD ±280ms — BAD는 BPM 156의 8분음표 간격 192ms보다 넓음) SS/숙련의 위상이 흐려지고, 판정 피드백이 "맞음/틀림"만 회신할 뿐 **방향성(빠름/늦음)**을 게임 중에 알려주지 않아(연습 모드에서만 텍스트 표시) 실력이 쌓이는 감각이 없다. 또한 풀콤보/올퍼펙트 같은 2차 목표가 결과 화면에 존재하지 않고, 노트 가시 시간이 하드코딩(1,600ms)되어 고밀도 레벨의 가독성을 플레이어가 통제할 수 없다 — 즉, 리서치 (1)-3 즉각 피드백, (1)-4 숙련 추적(커뮤니티 설문 최다 동기), (2) 개조 패턴 세 축이 모두 미구현 상태다.

**스프린트 목표 3줄 요약**: (1) 판정을 표준 수치로 재조정하고 빠름/늦음 오차바로 피드백을 완성한다, (2) FC/PFC 배지와 콤보 마일스톤으로 "클리어 위의 목표"를 만든다, (3) 스크롤 스피드 개조로 채보 수정 없이 체감 난이도·가독성 폭을 넓힌다.

## 2. 개선 항목 (우선순위 순, 총 규모 M+M+L)

### 항목 1. 판정 윈도우 재조정 + 얼리/레이트 오차바 — **M** (리서치 아이디어 #1)

#### 배경 (리서치 근거)
- 리서치 (2): StepMania MARVELOUS ±16.6 / PERFECT ±33 / GREAT ±67 / GOOD ±83ms, ITG FANTASTIC ±22.5 / EXCELLENT ±45 / GREAT ±90~135 / WAY OFF ±180ms. 교훈 — "최상위 2판정은 프레임 단위로, 하위는 2~3배씩 넓게".
- 리서치 (1)-3: 판정은 0.1초 내 시각+청각 회신이어야 함. 현재 코드는 판정 **등급**만 팝업으로 회신하고 오차 방향은 연습 모드에서만 텍스트(`hud-timing`)로 보여준다.
- 코드 검증: 현재 윈도우는 `PERFECT_WIN=55, GREAT_WIN=110, GOOD_WIN=185, BAD_WIN=280` (557행)으로 표준보다 전 대역 1.5~2배 넓다. 특히 BAD ±280ms는 Lv9(BPM 156)의 8분음표 간격 192ms를 초과해 인접 노트와 판정대가 겹친다.

#### 명세 (정확한 수치)

판정 윈도우 (전 레벨/무한 모드 공통, 대칭 유지 — DDR A식 비대칭은 채택하지 않음, 코드 단순성 유지):

| 판정 | 기존 (ms) | **신규 (ms)** | 근거 | 점수 (변경 없음) | HP (변경 없음) | 콤보 (변경 없음) |
|---|---|---|---|---|---|---|
| PERFECT | ±55 | **±45** | 60fps 2.7프레임, ITG EXCELLENT와 동일 | +100 | +4 | 유지 |
| GREAT | ±110 | **±90** | ITG GREAT 하단 | +75 | +3 | 유지 |
| GOOD | ±185 | **±135** | ITG GREAT 상단선 | +50 | +2 | 유지 |
| BAD | ±280 | **±180** | ITG WAY OFF / DDR BOO | +10 | +0 | 유지* |
| MISS | BAD 초과 미입력 | **BAD(180) 초과 미입력** | 상수만 바꾸면 자동 적용 | 0 | −8 | 끊김 |

\* 현행 규칙 유지: BAD도 콤보가 이어짐(`_registerHit` 806행). FC 정의(항목 2)가 이 규칙에 종속되므로 이번 스프린트에서 BAD 콤보 룰은 건드리지 않는다.

검증 포인트: 신규 BAD ±180 < 192ms(BPM 156 8분음표) → 최고 레벨에서 인접 노트 판정대 비침 없음. 무한 모드의 미스 임계는 `BAD_WIN+150`(1181행)으로 상수 종속이므로 자동 따라감.

**오차바 (얼리/레이트 인디케이터) 명세:**
- 데이터: 기존 `this.lastTimingMs`(794행, `positive=late / negative=early`)를 그대로 사용 — 신규 계산 로직 없음.
- 렌더: 판정선 아래 중앙에 수평 게이지 — 중심 (W/2, HIT_Y+62), 폭 160px, 높이 6px. 좌측 끝=−135ms(빠름, #38BDF8), 우측 끝=+135ms(늦음, #FF6B6B), 중앙 흰 틱=0. 마커(높이 12px 막대)는 해당 판정 색상(PERFECT gold / GREAT sky / GOOD green / BAD coral). |오차|>135ms(BAD)면 게이지 끝에 고정 표시.
- 표시 시간: 판정 후 500ms 페이드아웃 (`this.lastHitElapsed` 신규 필드 1개 추가, `_registerHit`에서 기록).
- 적용 범위: **모든 모드 상시** (`G.motionOn=false`에서도 표시 — 정보성 UI이므로 모션 축소 대상 아님). 연습 모드의 기존 HUD 텍스트(856~859행)는 병행 유지.
- MISS에는 마커 없음.

#### 구현 포인트 (실제 이름)
- `PERFECT_WIN/GREAT_WIN/GOOD_WIN/BAD_WIN` 상수 4개 (557행) — 유일한 소스이며 `handleKey`(788~793), `_tick` 미스 처리(736), 렌더 컬링(899, 924), `InfiniteGame._tick`(1181)이 모두 상수 참조 → 값 교체만으로 전파.
- `Game.lastTimingMs` (655, 794행) + 신규 `Game.lastHitElapsed`.
- `Game._render()` 내 신규 메서드 `_drawErrorBar(c)` 호출부 추가 (receptors 렌더 후, 918행 부근).
- `showResults()`(1510행)에 빠름/늦음 통계 1줄 추가: `_registerHit`에서 `errEarly/errLate/errSum` 카운트 → 결과 화면 Accuracy 칸(326행) 아래에 "빠름 n · 늦음 m (평균 ±x ms)". 이 수치가 기존 오프셋 UI(238~244행)의 수동 보정 근거가 된다.

#### 수용 기준
- [ ] BPM 156(Lv9)에서 8분음표 연타가 GREAT 연속 판정으로 처리되고, BAD 판정대가 인접 노트 판정과 겹치지 않는다.
- [ ] 모든 모드에서 노트 판정 후 오차바가 약 0.5초 표시되며, 왼쪽=빠름/오른쪽=늦음이 직관적이다 (연습 모드 HUD 텍스트 유지).
- [ ] 결과 화면에 빠름/늦음 횟수와 평균 오차가 표시된다.
- [ ] 윈도우 축소 후 홀드 노트 판정·홀드 브레이크·미스 팝업 타이밍에 회귀가 없다 (BAD_WIN 산술 의존부 전수 확인).
- [ ] 점수/HP/콤보 공식과 기존 저장 데이터(bc_scores)가 변경되지 않는다.

#### 규모: **M** (상수 조정은 S이나, 캔버스 신규 UI + 전 모드 검증 포함 M)

### 항목 2. FC/PFC 라벨 + 콤보 마일스톤 — **M** (리서치 아이디어 #5)

#### 배경 (리서치 근거)
- 리서치 (1)-4: "숙련 추적과 자기향상 — 재도전으로 눈에 보이는 기록 향상"이 커뮤니티 설문 최다 동기. (2): "FC/PFC를 결과화면에 명시해 별도 목표로 승격". (3): 리듬스타K식 "클리어→풀콤보→S랭크→올퍼펙트" 계층 분리.
- 코드 검증: 결과 화면에 Max Combo **수치**만 존재(325행, `res-combo`)하고 FC/PFC 개념이 전무. 콤보 50/100은 결과 후 업적 토스트로만 회신(463~464행)되어 리서치 (1)-3의 "즉각적 피드백"이 플레이 중엔 없음. 레벨 카드에는 최고 점수·등급만 표시(1272, 1288행).

#### 명세 (정확한 수치)

**FC/PFC 정의** (현행 콤보 규칙과 정합 — BAD는 콤보 유지):

| 라벨 | 조건 (클리어 시에만) | 색 |
|---|---|---|
| **PFC** (Perfect Full Combo) | `judge.PERFECT === total` (전 노트 PERFECT) | gold (#FFD700) |
| **FC** (Full Combo) | `judge.MISS === 0` (콤보가 한 번도 끊기지 않음, BAD 포함 허용) | silver (#C0C0C0) |

- 게임오버 시 미표시. PFC는 기존 업적 `perfect_only`(465행)를 자동 충족한다(PFC ⇒ MISS/BAD/GOOD=0).
- 결과 화면: Max Combo 칸 우상단에 배지 div (신규 `#res-fc`, 325행 부근). 텍스트 "PFC"/"FC", 등급 링(`res-grade-ring`)과 톤 통일.
- 영구 기록: 신규 `G.fcs = {레벨id: 'PFC'|'FC'}` — 상위 라벨만 유지(PFC > FC), `localStorage 'bc_fcs'` 신규 키. 레벨 카드의 `card-grade` 옆에 소형 마크 표시(`_renderLevels` 1272행 패턴 준용).

**콤보 마일스톤 (인게이지 연출):**
- 트리거: `this.combo`가 **50의 배수**(50/100/150/200/…)에 도달한 순간 1회 (`_registerHit`의 `combo++` 직후, `combo % 50 === 0`).
- 연출: 콤보 카운터(964~971행, W/2,65) 위쪽(y≈110)에 "50 COMBO!" 중앙 팝업 — 스케일인+페이드(`_render` 카운트다운 연출 996~1002행 패턴 준용), 지속 1초. 신규 필드 `this.milestoneFx = {n, life}` 1개.
- 이펙트: 중앙 링 1개 (`this.rings.push({x:W/2, y:65, ...})` 기존 rings 재사용) + 사운드는 **신규 오디오 코드 없이 기존 `sfxCountdown(0)`(526~530행, GO! 아르페지오) 재사용**.
- 일시정지 중에는 발화하지 않음(자명 — `_registerHit`은 정지 중 호출되지 않음). 레벨/무한 모드 공통 적용.

#### 구현 포인트 (실제 이름)
- `Game._registerHit` (800~813행): `combo++`(806행) 직후 마일스톤 체크 1줄 + 신규 `Game._milestone(n)`.
- `Game._render` (964행 콤보 블록 아래): `milestoneFx` 렌더 분기.
- `showResults` (1510~1618행): FC/PFC 산정(`g.judge` 기반, `g.gameOver` 가드), `#res-fc` DOM, `G.fcs` 저장 — 기존 bc_grades 저장 블록(1535~1540행) 옆 동일 패턴.
- `init` (1791~1808행): `'bc_fcs'` 로드 추가. `saveSettings`는 건드리지 않음(별도 키).
- `_renderLevels` (1262행): 카드 FC 마크 HTML 1줄.

#### 수용 기준
- [ ] MISS=0 클리어 시 결과에 FC 배지, 전 노트 PERFECT 클리어 시 PFC 배지가 표시된다 (게임오버 시 미표시).
- [ ] PFC/FC 최고 기록이 레벨 카드에 표시되고 재접속 후에도 유지된다 (localStorage 'bc_fcs', PFC가 FC를 덮어쓰지 않음).
- [ ] 50 콤보마다 인게이지 팝업+효과음이 정확히 1회 발생하고, 콤보가 끊긴 후 재달성 시 다시 발생한다.
- [ ] 점수 공식(콤보 보너스 포함)·15개 업적·기존 저장 데이터에 회귀가 없다.
- [ ] 무한 모드에서도 마일스톤이 동작한다.

#### 규모: **M**

### 항목 3. 스크롤 스피드 개조 — **L** (리서치 아이디어 #4)

#### 배경 (리서치 근거)
- 리서치 (2): 개조 표준 "스크롤속도 x0.25~x8.0, C모드" — (3) DDR 스피드모드. "채보 수정 없이 체감 난이도 확장".
- 코드 검증(중요): 기존 '속도' 개조(`G.speed` 0.5~1.5×, 230~237행)는 **BPM 자체에 곱해지는 음악 배속**이다(`_generate` 664~665행, `_tick` 714행에서 `bpm = lvl.bpm * speedMult`). 즉 **스크롤(가시 시간) 개조는 현재 존재하지 않으며**, 노트 낙하 시간은 `NOTE_FALL_TIME=1600`ms로 하드코딩(556행)되어 5곳에서 직접 참조된다. Lv8~9(8분박, density .80~.86)에서 가독성을 플레이어가 조절할 수단이 없다.

#### 명세 (정확한 수치)

**스크롤 옵션** (기존 UI 패턴과 동일한 칩 셀렉터):

| 옵션 값 | 라벨 | 낙하 시간 (NOTE_FALL_TIME÷) | 용도 |
|---|---|---|---|
| 1.0 | 1.0× | 1600ms | 기본 (현행과 동일) |
| 1.5 | 1.5× | ≒1067ms | 표준 리듬게임 감각 |
| 2.0 | 2.0× | 800ms | 고밀도 가독 |
| 3.0 | 3.0× | ≒533ms | 숙련자 |
| 4.0 | 4.0× | 400ms | 최상위 (상한 — 리서치 x8은 절차 채보 특성상 과잉) |

- 신규 상태 `G.scroll = 1.0` (기본). **`n.time`(노트 타이밍), 판정 윈도우, 음악/BPM/메트로놈은 전혀 변경되지 않는다** — 렌더 전용 파라미터. 타이밍 베이스 무변경 (하드 컨스트레인트 준수).
- 연산 위치: 신규 `Game._fallTime()` 메서드 1곳으로 집약 → `return NOTE_FALL_TIME / (G.scroll || 1);` — 아래 6곳의 `NOTE_FALL_TIME` 직접 참조를 교체:
  1. 활성 홀드 바디 progress/endProg (885~886행)
  2. 대기 홀드 바디 + 컬링 `dt>NOTE_FALL_TIME` (898~902행)
  3. 탭 노트 + 컬링 `dt>NOTE_FALL_TIME` (922~925행)
  4. 비트 라인 `_renderStage` `k*beatMs-this.elapsed<NOTE_FALL_TIME` (1039행)
  5. **`InfiniteGame._tick` 청크 보충 워터마크 `this._genUpTo<this.elapsed+NOTE_FALL_TIME+1500` (1132행)** — 고속 스크롤에서 `_fallTime()+1500`으로 수정하지 않으면 노트가 생성 전에 화면에 등장(팝인)한다. 본 항목 최대 리스크 지점.
  6. 미스 노트 잔상 컬링은 `BAD_WIN` 기준(899, 924행)이라 무수정 — 확인만.
- UI: mod-panel에 '스크롤' 행 신설(230~237행 `data-speed` 칩 패턴 준용, `data-scroll` + `setScroll(v)`), `saveSettings`(1691행)에 `scroll` 필드 추가, `init`(1798~1807행) 로드 + `_syncSettingsUI`(1695행) 동기화. `bc_settings`에 키가 없으면 1.0 (하위 호환).
- UX 혼동 방지: 기존 '속도' 행의 라벨을 **'배속'**으로 변경하고 설명 문구에 "음악·채보 밀도가 빨라집니다" / 신규 '스크롤' 행에는 "노트 낙하 속도만 조정 (판정 불변)" 병기.
- 스프라이트 폴백 유지: `_drawNote`(1054~1063행) 시그니처·폴백 로직 무수정 — 좌표만 달라짐. C모드(가시시간 고정)는 이번 스프린트 범위 외.

#### 구현 포인트 (실제 이름)
- `G.scroll` (447행 부터 G 객체), `Game._fallTime()` 신규, `_render`/`_renderStage`/`InfiniteGame._tick` 참조 교체.
- `setScroll(v)` 신규 + mod-panel HTML (221~261행) + `saveSettings`/`init`/`_syncSettingsUI`.
- 결과 화면 부제(1559~1560행)의 effBpm 표기는 기존 배속 기준 유지 (스크롤은 표기 대상 아님).

#### 수용 기준
- [ ] 스크롤 4.0×에서 9개 레벨 + 무한 모드 전체에서 노트가 판정선 도달 전 화면에 완전히 렌더되고, 무한 모드에서 노트 팝인(청크 지연)이 없다.
- [ ] 스크롤 값이 판정 결과에 영향을 주지 않는다 — 동일 입력 시퀀스에서 판정 분포·`lastTimingMs`가 1.0×와 동일하다.
- [ ] 설정이 저장/복원되고, 구버전 bc_settings(scroll 키 없음)에서 1.0으로 안전 시작한다.
- [ ] 노트 스프라이트 미로드 시 벡터 화살표 폴백에서도 동일 스크롤이 적용된다.
- [ ] 연습 모드(0.5× 배속)·미러·무적 개조와 조합 시 이상 없다.

## 4. 리스크

1. **윈도우 축소에 의한 전반적 성적 하락** (항목 1): 저장 등급(SS 등)은 자동 갱신되지 않지만 신규 플레이의 등급·클리어율이 하락해 진입장벽이 될 수 있음(리서치 (1)-5 박자 추적 보완성과 충돌 가능). → 완화: 출시 후 Lv1~3 클리어율 확인, 필요 시 GOOD ±135→150 등 **상수 1줄 핫픽스** 경로 확보(구조 변경 아님). 무적/연습 모드 안내 문구로 보완.
2. **무한 모드 청크 팝인** (항목 3): 워터마크(1132행)를 `_fallTime()` 기반으로 바꾸지 않으면 2.0× 이상에서 노트가 갑자기 나타남. → 수용 기준 1로 필수 검증, 발견 시 해당 줄만 수정.
3. **'배속' vs '스크롤' 이중 개조 혼동** (항목 3): 기존 플레이어는 '속도'가 음악 배속임을 모를 수 있음. → 라벨 변경('속도'→'배속')+설명 문구 병기로 흡수.
4. **FC 정의의 규칙 결합** (항목 2): "BAD가 콤보를 유지한다"는 현행 룰에 FC 정의가 종속됨. 추후 BAD 콤보 브레이크로 바꾸면 FC/PFC 정의와 배지 재산정 필요 — 본 문서에 명시했으므로 후속 팀이 인지 가능.
5. **저장 데이터 호환**: 신규 키 'bc_fcs' 추가와 bc_settings 확장은 하위 호환이지만, 구버전→신버전→구버전 롤백 시 scroll/fcs 키가 남는다(무해 — 파서가 미지 키 무시, 1798~1807행 화이트리스트 방식).
6. **단일 파일 코드량**: 목표 증분 HTML ≲20줄, JS ≲130줄. `_render` 분기 증가로 저사양 기기 프레임 영향은 미미하나(조건 분기 1회/프레임), 오차바는 `G.motionOn`과 무관히 그려지므로 모션 최소화 사용자에게도 정보성 이점으로 커뮤니케이션.
